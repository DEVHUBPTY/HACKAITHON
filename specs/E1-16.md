# E1-16 · Revisión humana, versiones y exportación a Notion

**Rol:** P · **Depende de:** E1-15, E1-10b

## Objetivo
Implementar la etapa 7: una persona responsable **acepta, corrige o descarta** cada caso; todo queda registrado con versiones; y la ficha se crea o actualiza en Notion mediante exportación manual.

**Por qué importa:** Es la etapa 7 del reto y el control humano obligatorio de la sección 8. Los tres verbos del PDF (aceptación, corrección, descarte) deben convivir con los cinco estados de la sección 8.

## Punteros de contexto
- PDF sección 3 (etapa 7), sección 7 (`fichas.jsonl`) y sección 8 (control humano)
- Decisiones D-46 a D-51
- `src/revision.py`, `src/exportar.py`, `templates/ficha.md.j2`
- `config/revision.yaml` (revisores y roles, motivos de descarte, transiciones permitidas)
- Base *Casos y evidencias* de Notion

## Restricciones
- **Acciones → estados (D-46):** abrir → en revisión; aceptar → aprobado como borrador; corregir → nueva versión, sigue en revisión; pedir evidencia → requiere evidencia (con vínculo a los vacíos); descartar → descartado con **motivo obligatorio** de la lista; reabrir → en revisión con motivo
- Transiciones permitidas solo las de `config/revision.yaml`; no existe ningún estado después de 'aprobado como borrador'
- Un grupo `GRP-` pasa a caso `CASO-` (ID estable) cuando se abre para revisar
- **Registro de solo agregar (D-47):** tabla `revisiones` con caso, versión, acción, estado anterior y nuevo, revisor, rol, fecha UTC, comentario, motivo y diferencias; nunca se actualiza ni se borra una fila; el estado actual es la última fila
- **Corrección (D-48):** el texto corregido se revalida con el validador; las advertencias se muestran y la persona debe confirmarlas; se guardan la versión original y la corregida
- Regenerar un borrador nunca sobrescribe una versión corregida: crea otra versión
- **Revisor (D-49):** se elige de la lista de `config/revision.yaml` con su rol; no hay autenticación (fuera de alcance) y se declara como limitación
- La app (DuckDB) es la fuente de verdad; Notion recibe exportaciones
- La persona puede rechazar un vínculo oficial mal aplicado; queda registrado y no se usa en el borrador
- **Notion (D-50):** botón 'Exportar a Notion' genera el Markdown con Jinja2 y una fila CSV para *Casos y evidencias*, con ID `CASO-`, versión, fecha de exportación, historial de revisión y leyenda de alcance (D-51); si el caso ya existe se actualiza esa página. Automatizar con la API es E3-03 (opcional)
- El botón dice 'Aprobar como borrador' y la ficha aprobada mantiene la marca BORRADOR
- `fichas.jsonl` con los campos exactos del contrato; `estado_revision` = última fila de `revisiones`
- Misma lógica para banca; el revisor es el analista

## Listo cuando
- Test: cada acción produce el estado correcto y las transiciones no permitidas se rechazan
- Test: descartar sin motivo → rechazado
- Test: la tabla `revisiones` solo crece; ninguna fila se modifica
- Test: una corrección con un dato sin cita genera advertencia y queda registrada si se confirma
- Test: regenerar después de corregir crea una versión nueva y conserva la corregida
- Test: un vínculo rechazado no aparece en el borrador regenerado
- Test: cada línea de `outputs/fichas.jsonl` valida contra el esquema del contrato
- `poetry run python -m src.exportar --caso CASO-001` genera Markdown y fila CSV con versión, historial y leyenda
- `poetry run python -m eval.revision` reporta tasas de aceptación, corrección y descarte, motivos de descarte, tiempo de revisión por caso y % de afirmaciones editadas
- `poetry run pytest -v` pasa completo y se hizo la revisión de `docs/REVISION.md`.
